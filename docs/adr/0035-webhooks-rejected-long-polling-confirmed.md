# ADR 0035: Webhooks rejected, long polling confirmed

- Status: rejected (for now)
- Date: 2026-09-15

## Context

ADR 0003 chose long polling in one line ("requires exposing a TLS endpoint; unnecessary
complexity for a single low-traffic bot on a VM"). The question came back after a year of
operation, partly prompted by reminders that *looked* late — so the first thing worth
recording is that the two are unrelated: reminders are outbound `sendMessage` calls driven
by the `JobQueue` (ADR 0005), and the channel through which updates are *received* does not
touch them by a millisecond. The actual cause of that symptom is in the amendment to ADR 0005.

What remained was whether webhooks are worth it on their own merits, given the current
runtime: two bots (dev and prod) as Docker containers on one Oracle Always Free VM, with
`.env` and `compose.yaml` regenerated by the deploy pipeline (ADR 0010) and no public HTTP
surface at all.

## Decision

**Stay on long polling.** Keep `application.run_polling()`; add no public endpoint, no TLS
material, no reverse proxy.

What webhooks would actually buy at this traffic level:

- No `getUpdates` cycle (today roughly one request every 10s per bot while idle) — traffic
  and CPU that are already negligible on this VM.
- Receive latency in the order of milliseconds: long polling holds the connection open and
  Telegram answers as soon as an update exists, so there is nothing perceptible to gain.
- Headroom for high update volume. Today the volume is a few dozen updates a day.

What it would cost:

| Cost | Detail |
|---|---|
| Public surface | Port 443/8443 open: Oracle security list **and** the Ubuntu image's iptables — persistent rules, hand-managed on the VM, which is the opposite of ADR 0010 |
| TLS | Either a domain plus Caddy/nginx with ACME (~€10/year, one more service in the compose file), or a self-signed certificate uploaded via `setWebhook` (free, but rotation and re-`setWebhook` by hand) |
| Two instances | dev and prod on one VM means two endpoints (distinct ports or paths) and two secret tokens, across two GitHub environments |
| Dependency | `python-telegram-bot[webhooks]` pulls in `tornado`, not in the lock file today |
| Config | `UPDATE_MODE`, `WEBHOOK_URL`, `WEBHOOK_PORT`, `WEBHOOK_SECRET_TOKEN` in `config.py`, in the pipeline-generated `.env`, in the env table of ARCHITECTURE.md and in DEPLOY.md |
| Failure mode | Polling recovers from a network fault on its own. With a webhook, a dead endpoint or an expired certificate makes Telegram retry and then **discard** updates, with no local trace: it takes `getWebhookInfo` to notice. The bot goes mute, quietly |
| Local development | `uv run python -m fantaformazionibot` runs anywhere behind NAT today; a webhook needs a tunnel (ngrok/cloudflared) or a polling branch kept alive anyway |

That is roughly a session of code plus VM work the pipeline cannot automate, plus permanent
operational debt, for no functional gain.

## Alternatives considered

- **Webhook with a self-signed certificate on the VM's IP**: the zero-cost variant, PTB can
  serve TLS itself (`run_webhook(cert=..., key=...)`). Rejected: manual certificate rotation
  whose failure mode is a silently mute bot.
- **Webhook behind a domain and a reverse proxy**: cleaner, with automatic renewal, but adds
  a service to the compose file and VM state the deploy pipeline does not own.

## Consequences

- ADR 0003's choice stands, now with numbers behind it rather than an aside.
- Two Telegram bots remain mandatory for dev and prod: polling forbids sharing a token.
- This is worth reopening if any of these change:
  1. The bot gains a public HTTP surface for something else (Mini App, dashboard, OAuth) —
     the infrastructure cost is then already paid.
  2. It moves to an event-driven host with no always-on process — which would also need a
     replacement for the `JobQueue`, making it a redesign rather than a switch.
  3. Update volume grows enough for `getUpdates` to queue (measurable: the lag between a
     message's `date` and its handling in the logs).
  4. Telegram changes the terms of `getUpdates`.
